COMP6006 Final Assignment Part B
Critical Analysis of Real-Time Web Application Design
Conference Connect

Question 1: Analysis of SPA Architecture and State Management

The frontend of Conference Connect was implemented as a React single page application using Vite, React Router, and React-Bootstrap. The architecture was intentionally kept simple because the assignment focuses on demonstrating core SPA, authentication, and real-time communication concepts rather than building a large production system. The application is organised into pages, reusable components, context providers, and small helper modules. The main routes are defined in App.jsx, while individual screens such as Login, Dashboard, My Schedule, Active Sessions, and Live Session are separated into the pages folder. Reusable interface elements such as the navigation bar, protected route wrapper, and session card are placed in the components folder.

This structure improves maintainability because each file has a clear responsibility. For example, SessionCard is reused on both the dashboard and the schedule page, which avoids repeating card layout logic. ProtectedRoute centralises the route protection check, so each protected page does not need to manually check whether the user is logged in. The navigation design is also simple: unauthenticated users are sent to the login page, and authenticated users can access the dashboard, schedule, active sessions, and live session routes.

State management was handled with React's built-in state and context rather than Redux or another external state library. AuthContext stores the currently logged-in user and exposes login/logout-related functions. ScheduleContext stores the list of saved session IDs and persists them in browser localStorage. This is suitable for the scale of the assignment because the state is small and easy to understand. The sessions themselves are fetched from the backend API, while live room state is handled separately through Socket.io events.

The main advantage of this approach is that it is easy to explain and debug. State changes are close to the components that use them, and the context providers avoid passing props through many levels of the component tree. Using localStorage for the schedule also means that a user's selected sessions remain available after refreshing the browser. However, this design has limitations. The schedule is not stored on the server, so it is tied to the browser rather than the authenticated LinkedIn account. If the same user logs in on another device, their schedule will not follow them. Also, as the application grows, putting more global state into context could make the frontend harder to manage. In a larger system, a clearer state strategy or server-side persistence would be needed.

The routing design supports the user experience expected in an SPA because navigation between pages does not require full page reloads. React Router handles the routes /login, /dashboard, /my-schedule, /active-sessions, and /live/:sessionId. This matches the assignment's suggested routes and makes the application predictable during demonstration. React-Bootstrap was used for cards, buttons, badges, grid layout, forms, alerts, and navigation. The interface is deliberately basic, but it remains responsive through Bootstrap's Container, Row, and Col components.

Question 2: Analysis of Real-Time Communication Design

The real-time communication system was implemented with Socket.io on both the Express backend and the React frontend. Socket.io was chosen because it directly supports bidirectional event-based communication and room-based messaging, which matches the assignment requirement for separate live conference rooms. Each conference session has a session ID, and that ID is also used as the Socket.io room name. When a user joins a live session page, the frontend connects to the Socket.io server and emits a joinRoom event with the session ID.

The backend maintains an in-memory rooms map. Each room contains a participants map and a messages array. The participants map uses the socket ID as the key, which makes it simple to remove a participant when they leave or disconnect. The messages array stores chat history while the server is running. This design satisfies the assignment requirement that chat history should remain available during runtime but does not require permanent database storage.

The event design is intentionally direct. The frontend emits joinRoom when entering a room, sendMessage when submitting chat text, and leaveRoom when leaving the page. The backend emits chatHistory to the newly joined user, chatMessage to all users in the room, participants when the participant list changes, roomNotice when someone joins or leaves, and activeRooms to all connected clients when active room counts change. Socket.io rooms are used to ensure chat messages are only delivered to users in the relevant live session. For example, a message sent in the Practical React Patterns room is emitted only to that room, not to all connected users.

Participant synchronisation is handled on the server. This is preferable to letting each client maintain its own assumptions, because the server has the authoritative view of connected sockets. When a participant joins, leaves, or disconnects, the server updates the room's participants map and emits the updated participant list. The Active Sessions page listens for activeRooms updates, so participant counts update without requiring a page refresh. This satisfies the requirement that active room counts update automatically in real time.

A key challenge in real-time systems is handling disconnections correctly. Users may close a tab, refresh the page, lose connection, or move between rooms. The implementation addresses this by calling the same leaveCurrentRoom function for both leaveRoom and disconnect events. Also, when a socket joins a new room while already in another room, the server first removes it from the current room. This avoids a single socket being counted in multiple live sessions at the same time.

The main limitation is scalability. All active room data and chat history are stored in memory inside one Node.js process. This is acceptable for the assignment because a database is not required and the brief allows in-memory storage. However, it would not work well across multiple server instances because each instance would have its own separate room state. If deployed at larger scale, the application would need a shared adapter such as Redis for Socket.io, persistent database storage for messages and schedules, and better reconnection/session recovery logic. Message validation and rate limiting would also be needed to prevent spam or abuse.

Question 3: Authentication and Security Considerations

Authentication is implemented using Passport.js with LinkedIn OAuth through the passport-linkedin-oauth2 package. The LinkedIn app uses the current OpenID Connect scopes openid, profile, and email. After LinkedIn authentication succeeds, the backend stores a simplified user object in the Express session. The frontend checks the current user by calling /auth/user. If a user is authenticated, protected pages become available; otherwise, the ProtectedRoute component redirects the user to /login.

The backend also includes a local demo login route. This was added because the lecturer advised students to support local authentication for testing multiple linked accounts during development and demonstration. The demo login is not treated as a replacement for LinkedIn OAuth. It is clearly labelled as a Demo/Test Login on the login page and is useful for opening different browsers or private windows with different attendee names to test Socket.io participant counts and chat behaviour.

Route protection exists on both the frontend and backend. On the frontend, ProtectedRoute prevents unauthenticated navigation to the dashboard, schedule, active sessions, and live room pages. On the backend, requireAuth protects the sessions API. Socket.io also checks the Express session before allowing a socket connection to continue. This means unauthenticated users should not be able to join live rooms or send chat messages through the normal application flow.

The design has several strengths. LinkedIn credentials are stored in environment variables, and the real .env file is excluded from git. The session cookie is HTTP-only, which reduces exposure to client-side JavaScript. CORS is restricted to the configured frontend URL and credentials are enabled so the browser can send the session cookie to the backend. Logout destroys the session and clears the cookie.

There are also limitations. The session store is the default in-memory Express session store, which is not suitable for production. In production, a persistent session store such as Redis or a database-backed store would be required. The cookie is configured with secure: false because the application runs on localhost over HTTP. In production, HTTPS should be used and secure cookies should be enabled. The demo login is intentionally weak and should not exist in a production deployment. The application also does not implement CSRF protection, rate limiting, or detailed input sanitisation beyond trimming empty messages. These are acceptable simplifications for the assignment but should be improved in a real system.

Question 4: Critical Reflection and Future Improvements

The most technically challenging part of the implementation was coordinating authenticated Socket.io connections with Express sessions. The application needs to ensure that only authenticated users can join live rooms, while still allowing real-time updates after the initial HTTP login flow. This required sharing the Express session middleware with Socket.io and checking the Passport user stored in the session before accepting socket activity. Once that link was working, the room logic became easier to reason about.

A second challenge was designing the live room events so they remained simple but complete. The system needed to support multiple rooms, chat history, participant lists, active room counts, and join/leave notices. The trade-off was to keep all room state in a simple in-memory map rather than adding a database. This made the code easier to explain and matched the assignment note that permanent storage is not required. The disadvantage is that all live data resets when the server restarts.

Several trade-offs were made deliberately. The UI is basic and uses standard Bootstrap components because the assignment asks for React-Bootstrap and responsive design, not advanced visual design. The schedule is stored in localStorage because it demonstrates dynamic frontend state without adding unnecessary backend complexity. The local demo login was included for testing multiple accounts, but LinkedIn remains the main OAuth option for the authentication requirement.

If this system were developed for production, the first improvement would be persistent storage. Users, schedules, sessions, chat messages, and room history should be stored in a database. The second improvement would be a production-ready session store and stronger cookie settings over HTTPS. The third improvement would be a scalable Socket.io setup using a Redis adapter so multiple backend servers can share room events and participant state. Other useful improvements would include message moderation, rate limiting, richer session search/filtering, better error pages, and automated frontend tests. Overall, the implementation meets the assignment goals by demonstrating a React SPA, protected routing, Passport-based LinkedIn authentication, Socket.io rooms, participant synchronisation, and dynamic UI updates while remaining simple enough to explain during a demonstration.
